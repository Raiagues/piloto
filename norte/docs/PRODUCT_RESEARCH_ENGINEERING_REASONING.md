## Discovery alternatives

Interaction counts below are design estimates from an empty workspace, not measured results. All approaches require the same explicit scenario analysis and never update the baseline automatically.

| Approach | Interactions | Learnability / footprint | Meeting speed / ambiguity | Baseline connection |
| --- | --- | --- | --- | --- |
| **Write a hypothesis on a card → contextual impact action** | Write + one action for resolved values | Keeps the existing click-to-write behavior; one local action | Immediate for an unambiguous numeric change; unresolved replacements retain an editor | Changed entity and value are visible in the temporary scenario; baseline is preserved |
| Select a system entity → what-if → edit value | Select + action + edit + run | Predictable but requires finding the object first | Precise and fast when already inspecting System | Strong: starts at a known entity |
| Global natural-language command palette | Open + write + resolve + run | Small when closed, but the command must be discovered | Flexible; hidden commands and unrestricted interpretation increase ambiguity | Requires a separate target-resolution step |

**Choose the contextual card hypothesis for Discovery.** It makes writing useful before demanding system navigation. The later product-principles specification removes redundant confirmation for unambiguous numeric changes: the impact action runs the deterministic engine immediately and shows the resolved target/value in the scenario. In System, the contextual editor starts from the selected object. Restrict recognition to supported entity/property/value patterns; relative percentage increases and ambiguous targets cannot silently become absolute changes. Unrelated notes remain quiet. Component alternatives with missing specifications retain the editor and produce missing-data questions, never invented numbers.

## Provenance and focus

Use two levels of disclosure: a compact node with an explicit information affordance, then a focused technical dialog containing values, dependencies and source excerpts. The dialog retains the graph behind it and restores focus when closed; its bounded width also supports smaller screens. Clicking a value's source or a relation exposes its evidence inside this context. Hover may explain an icon but cannot be the only access path. Keep excerpts short, highlight the cited text, and show a locator only when actually known.

The graph remains full width when information is closed. Clicking a subsystem focuses its children; a breadcrumb returns to the parent. Zoom navigates the canvas and does not unexpectedly change the architecture. During analysis, show only the relevant path and immediate supporting context, with labels as well as color. Requirements remain outside normal architecture nodes; their overlay can dim unrelated entities and highlight linked edges without losing the graph position.

## Document-processing scope

Google's [Generate Content document guide](https://ai.google.dev/gemini-api/docs/generate-content/document-processing) documents inline PDF content for the endpoint already used by Norte. It describes other document inputs as text, without reliable preservation of visual structure. Norte can decode UTF-8 text/Markdown/CSV/JSON/code itself and provide bounded PDF data to Gemini. This does not establish reliable DOCX/XLSX parsing in the current integration; keep those explicitly unparsed and ask for PDF/CSV/text exports. The [structured-output guide](https://ai.google.dev/gemini-api/docs/structured-output) supports schema-based responses, but schema conformance alone does not verify an engineering claim or source quotation.

## UX decisions for Norte

1. **Automatic conception initialization:** `Start conception` reads linked Project Memory artifacts, extracts architecture plus requirements, saves the result, and opens System. Show an honest indeterminate activity state; failure offers retry or a return to Memory, never a fabricated model.
2. **System → Timeline → Discovery BETA:** first entry answers what Norte understood. Persist the last workspace for later visits. The ordering is an application of the shared-model review pattern, not a claim that another tool prescribes these tabs.
3. **Project-owned progression:** persist unlocked phase separately from current route, together with baseline/memory revision metadata. A memory update may indicate staleness but must not silently rebuild the model.
4. **One project selection:** the project's team is read-only context. This removes a redundant selection and prevents disagreement between project and team state.
5. **Macro architecture with explicit drill-down:** reuse Dagre and existing canvas navigation. Keep requirements and most properties outside normal graph nodes.
6. **Intentional details:** selection highlights; the explicit information affordance opens a compact dialog. Do not reserve a permanent details column.
7. **Requirements overlay:** a small count opens a searchable list; one filter surface contains editable, generic facets. Selecting a requirement highlights linked entities/relations, including those affected in a scenario. Preserve original source provenance after edits.
8. **Quiet contextual Discovery:** keep free writing, movement, pan/zoom/fit and history. Replace global organization and change buttons with the contextual technical hypothesis action chosen above.
9. **One shared scenario engine:** resolved values reveal temporary causal paths immediately; unresolved changes retain a compact editor. Clearing restores the workspace. Explicitly saved scenarios persist separately from the baseline.
10. **Auditable conclusions:** critical requires supported facts and a concrete rule/comparison. Missing information remains review; checked compatibility can be valid. Expose inputs, normalized units, rule, calculation, traversed relation IDs and citations. AI inference adds short justification, confidence, model and time, never hidden chain-of-thought.

Validation should measure task completion time, dependency recall, critical-impact precision, unsupported-claim rate and traceability coverage. These are planned metrics; this research did not measure them.

## Product-principles and Quetzal follow-up

The subsequent specification makes autonomy, expert correction, visual reasoning, observability and time-to-value product constraints. These principles guide the changes without copying another product's interface. Project Memory already builds System automatically; project membership configuration is no longer required to begin engineering review. Memory revisions continue to expose changed documents without silently replacing expert corrections.

Expert corrections now retain the initial suggestion, previous and corrected states, source snapshots and project/baseline context in an exportable history. No training pipeline or machine-learning controls are exposed. The Quetzal validation context is seeded as ordinary Project Memory; evaluator-only expectations and on-orbit observations are isolated outside runtime imports.

The browser fixture test measures one action from a saved, recognized engineering hypothesis to visible impact and zero configuration steps after Memory. Its recorded timings describe local automation with a mocked extraction provider, not a student experiment or provider latency. Technical extraction and reasoning are evaluated separately by the [Quetzal benchmark](VALIDATION_QUETZAL1.md); independent engineering review of the evaluation reference remains pending under the user-approved [V0.1 specification](VALIDATED.md). A0 means curated context, while A1 raw-artifact ingestion remains unmeasured. Boundary cases and masked structure checks isolate quantitative behavior; historical reconstruction and the contamination probe carry explicit limits. The benchmark scope is EPS/COMMS with only the required electrical consumers, while broader subsystem and student studies remain sequenced follow-ups.
