## Evaluation policy

The UI's confidence percentage is the probability assigned to the displayed answer. For Noul false it is `1 - noul`, so a 7% true result displays **false · 93%**, not false · 7%. For Choice/Score it uses the selected class/level probability. The TypeSafe API's separate `confidence` statistic is not substituted for that probability. [Official confidence documentation](https://docs.typesafe.ai/confidence) distinguishes these quantities and discusses setting thresholds per question and application risk.

An execution passes a question only if its predicted answer matches the expected answer and the expected answer's probability reaches the configured minimum. A wrong answer remains wrong even with a low threshold. A correct answer below that threshold is explicitly labeled **Falhou · resposta correta, confiança insuficiente**. Thresholds remain editable and are not sent to the API. Existing 60–90% example thresholds are provisional acceptance rules, not empirically calibrated accuracy guarantees; none were fitted downward to make this spreadsheet pass.

For expected Score levels, the predicted answer is the unique most probable level, not the rounded weighted Score. Tied levels do not pass. The full original response/distribution remains in saved history; CSV retains the fractional score and expected-answer probability. This application-level discrete policy must be kept fixed when comparing versions. TypeSafe describes Score as a position that may fall between levels, with a separate distribution. [Official Score documentation](https://docs.typesafe.ai/primitives/score).

Summaries show the most frequent answer and its mean probability, with ties and varied answers indicated. Every run is evaluated separately: a high mean cannot hide a failing run. API errors and deleted runs are excluded from response averages. Results from different States are never averaged into a synthetic model answer.

## Suitability for project-event tracking

The question set covers event detection, event type, commitment, impact, and follow-up. It is useful as a small exploratory test, not yet a reliable general evaluation set:

1. **Context conflict:** every aluminum variant still says the current part is already 3 mm aluminum. Proposing aluminum can therefore be redundant. Keep this workbook suite unchanged for reproducibility, then add a separately named context variant with a genuinely different current material or no material specified.
2. **Implicit versus explicit pending decisions:** the workbook's broader question allows a future material decision to be inferred from a test proposal, while several labels expect false. Define whether inferred decisions count before interpreting these mismatches as model failures.
3. **Action-item ambiguity:** the workbook treats switching the final design as an action but not merely reporting a result. Phrasings such as “Let's use…” can be a suggestion or a commitment without evidence of agreement. Add paired cases with explicit agreement, assignment, and negation.
4. **Impact needs scope:** a material change may affect one component or the whole design; the same short utterance does not establish safety/cost breadth. Add project scope in State or treat those examples as ambiguous review cases.
5. **Coverage:** six related English utterances do not cover negative/casual speech, repeated events, corrections, risks, requirements, multilingual input, or tracking updates. A real create-versus-update decision also needs existing tracked items in State; recent speech alone is insufficient.

Questions are evaluated independently against State; one answer does not condition the others. [Official introduction](https://docs.typesafe.ai/introduction). Therefore contradictory outputs are possible and require application validation or human review, not hidden answer correction. Do not tune questions and thresholds on these six examples and then report the same examples as independent validation. Use separate held-out conversations and record precision/recall of `should_track`, per-class errors, and the percentage routed to review at each threshold.
