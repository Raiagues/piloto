# Classification providers and temporal transcription windows

## Run

Use `./setup`, `./start` and `./stop`. **Official Jev is now the default**, using `https://api.typesafe.ai/v1/systemone` and `jev-latest`, per the [official API reference](https://docs.typesafe.ai/api). Put `TYPESAFE_API_KEY=...` in the root `.env`; `JEV_API_KEY` and the user's existing `JEV_KEY_API` are supported aliases. `.env.example` contains no secret. Setup never overwrites an existing `.env`, and `.gitignore` excludes private environment files. The parser does not execute shell code. Nonempty environment credentials take precedence over file values. `./start` also restarts this checkout's existing service to apply changes to `.env` and server code. No additional library or manual export command is required.

The local Python server serves the UI at http://127.0.0.1:8000. In official mode it does not download or start jevos. It reads the secret only server-side and sends it as a Bearer header over verified HTTPS to the fixed TypeSafe endpoint; redirects are refused. The browser sends State/Questions only to the loopback proxy, and never receives the key in health, output, backups or errors. GET and HEAD both deny private files, and the API checks Host, Origin, JSON content type and the expected provider. Health reads configuration only: `ready` means a key is present, not that authentication has been proven. A successful classification verifies the connection in that page. There are no periodic remote checks, automatic HTTP retries or fallback to the copy. Authentication, billing, rate-limit and timeout errors are explicit; fatal manual errors stop the rest of the selected repetitions. Official State/context/transcripts and questions leave the machine and consume API usage, as authorized by the user; each 1×/4×/10× run makes that many calls unless interrupted. Revisions in live recognition can also cause another billable classification.

To explicitly use the former local path, set `NORTE_PROVIDER=local` in `.env`. Only that mode runs the verified [jevos-v3 installer](https://github.com/feder-cr/jev/releases/tag/jevos-v3) (roughly 657 MB download / 755 MB installed, Linux x86_64) and owns a loopback child engine. Existing runtime files are retained, not deleted. `./stop` only targets a PID whose command, working directory and owner match this checkout, plus its owned engine if any.

## What changed

The old 180-word / 45-second conversation batches remain removed. Capture still uses 5–15 second windows. Model inputs now restore a bounded unfinished-sentence prefix from the same recognition result when a cut would leave trailing words alone. No previous turn, unrelated completed sentence, hidden summary or future word is retrieved. `depende_de_contexto` asks whether information is missing; it does not retrieve it.

The raw transcription log still separates reading rows by recognition result, punctuation and a 60-word readability limit. Those rows are not the inference batches. The Classifier State is the exact model input, including explicit same-utterance overlap. Raw windows and model inputs are both exported.

## Capture and cuts

- A window starts at detected speech (or the first recognition result when speech events are unavailable).
- Before 5 seconds, wait. At or after 5 seconds, 650 ms of detected quiet closes the window.
- Continuous speech is cut at 15 seconds; another window begins without stopping speech recognition.
- Manual pause flushes a short tail, even if under 5 seconds. Empty silent windows are not sent to the model.
- A 100 ms foreground timer advances windows; delayed ticks catch up using the fixed deadlines.
- The preferred pause signal is microphone RMS energy through Web Audio (threshold 0.015), with browser speech-start/end and final-result signals as fallbacks. This is approximate energy-based silence detection, not a learned speech detector.
- Background throttling, noise and browser speech-service delays can delay delivery. The logical window limit does not promise that text or classification is available exactly at 15.000 seconds.

The browser does not expose aligned word timestamps. Words inherit the time they first appear in a recognition hypothesis. When a final result revises old words, prefix/suffix matching retains previous window assignments. New appended words use the current event time. Thus these are event-aligned text windows, not precise audio slices. Timing and cross-boundary correction mapping are estimates.

### Preventing trailing-fragment inputs

A quiet gap may close a window before the browser delivers the last words of the same hypothesis. Previously a full bar-size request in the log could produce State = "de 5": raw word-arrival windows were used directly as independent model inputs.

`Cutter.view()` preserves raw source slices. Words arriving in VAD gaps are retained in the nearest same-take window rather than dropped. `classificationView()` restores the beginning of the unfinished sentence within each slice's recognition result, stopping at preceding sentence punctuation and never reading beyond the slice's end. Added prefixes are capped at 160 words and 4000 characters, with word-aligned boundaries and a `contextTruncated` flag. Existing server input-size limits still apply.

`windowText` is the raw fragment; `text` is the model input. `inputSources` gives exact source IDs/character offsets, `inputStartMs` identifies the earlier input start, and `context` is `same-utterance-prefix` when a prefix was added. No earlier turn, other take or completed previous sentence is included. This is bounded overlap, not a semantic completeness guarantee: separate final recognition results are not silently merged.

Raw windows still have a 15-second maximum; overlapping model input can refer to earlier speech. State and the request use identical text. Saved windows are reinterpreted on reload without deleting raw records or older model responses. Derived inputs are cached between revisions, not rebuilt on every timer tick.

The application does not save raw audio. Recognition may use the browser vendor's service and is not guaranteed offline. Classification is remote with official Jev by default; local inference is an explicit alternative.

## Meeting room: continuous capture and speech continuation

The meeting room (`meeting-room.js`, Simulação de vigas / Reuniões) no longer stops the browser recognizer on a 5-second clock. Each stop left the microphone deaf for about one second while it restarted, which dropped words in the middle of sentences (`de 12 | 13 cm` lost `para`). Chrome's continuous mode already confirms each phrase at a natural pause, so `CaptureWindow` (`speech-windows.js`) only forces a stop when unconfirmed speech stays pending for 15 seconds; silence never stops it. Manual pause and end of meeting still flush the tail.

Confirmed pieces are short and often cut mid-thought, so before a piece becomes a chunk `meeting-session.js` asks Jev (lane `speech`, `continuation: true`, audit in `record.segmentation`):

1. `speech_status` — has the speaker finished the point, or is the key content still missing (`o problema que a gente viu era`, `a gente testou e validou` without the outcome)? Unfinished (p ≥ 0.55) waits for the next piece and joins it. A literal open ending (preposition, `que`, …) skips the call.
2. `speech_join` — when the piece is finished on its own but the speaker is still talking (or the next piece is queued), does the next piece complete the same point (`… o limite que a gente definiu` + `que é 200 megapascal`)? Joins at p ≥ 0.6, comparing only the latest piece. A next piece that ends open (`e o resultado da última medição foi`) starts its own chunk.
3. `command_completion` — an instruction to Norte only absorbs its missing value or target (`Norte, muda a altura da seção para` + `30 centímetros`), never the conversation after it.

A chunk joins at most 6 pieces / 90 words; a pause longer than 6 s, another speaker, or a new instruction to Norte always ends it. If a check fails, the piece is processed as is (never dropped). Restoring a saved meeting accepts these wider groups only when the record carries the continuation audit.

Spoken Brazilian Portuguese commands are normalized and audited (`colloquial_imperative`): `compara`, `usa`, `tira`, `bota`, `adiciona` … map to the command forms, and a new force or distributed load said without a sense acts downward (`default_direction`).

`tests/live-meeting-simulation.cjs --run-live` speaks a long, ambiguous Portuguese meeting (half sentences, corrections, three topics, voice commands for the simulator and graphs) into the real page through a recognizer that behaves like Chrome (word-by-word interim results, confirmation at pauses, deaf while restarting) and uses real Jev calls. It checks that no word is lost, that each key fact reaches one chunk intact, that distinct facts are not fused, that every command applies and that the saved meeting reopens. Credentials come from `NORTE_USER` / `NORTE_PASSWORD`; the report is written to `.runtime/simulation/`.

## Real model, real outputs

The default integration uses [official TypeSafe Jev](https://docs.typesafe.ai/introduction). The previous [jevos](https://github.com/feder-cr/jev) implementation remains opt-in and is not the same model. Successful responses record `provider` and the actual returned model version. Existing `jevos-*` history is labeled local in tests, summaries, comparisons and exports; new official results are not relabeled copies. Each manual batch pins the provider, and a mismatch is rejected instead of mixing engines mid-batch. Incomplete saved live requests are not replayed automatically on reload; the user can retry explicitly.

`classifier-config.json` supplies editable questions for communication intent, relevance and missing context. Initial instructions are English because a small local comparison handled an obvious Portuguese question better with those prompts; that is not a general language-quality benchmark. The exact instructions appear in the UI and every request. No translation of the user's transcript is performed.

A closed window with available text is queued immediately, including provisional text, to reduce latency. If its text or confirmation state changes, that window is reclassified. An obsolete in-flight answer cannot overwrite a newer revision. Withdrawn text invalidates the displayed decision. Completed earlier revisions are retained in the JSON history. Raw source records remain intact.

Only one request is in flight per page. All configured questions are included in the same request. Queued revisions for a window are replaced by the newest revision, not appended endlessly. Newest queued windows have priority. Applying edited questions reclassifies the latest State, not the whole archive. Pending, running, error and model-offline states are explicit; errors have a retry button. Model responses are never fabricated from keyword rules.

`POST /api/classify` validates types, bounded question counts and criteria, forwards to the configured provider, and validates returned labels and probability ranges. UI payloads cannot select another endpoint or model. The response includes the exact request, actual response, provider and measured response latency (including network time when remote). Choice percentages use the selected label's probability, not `confidence`. Raw `confidence` remains in JSON as distribution concentration, not probability of correctness. `score` is an expected level; dots show each criterion and highlight the most probable level. `noul` displays P(true), not a generated Boolean. A compact 'Incerto' indicator appears when the top probability is below 50% or the top-two margin is below 15 percentage points. These are UI heuristics, not calibrated correctness estimates; raw probabilities and labels are unchanged. Score also shows its most probable level/probability, separately from the weighted mean. Portuguese quality still needs evaluation on actual meeting examples.

Archive v1 is extended to read both legacy text States and structured States; no saved data is migrated or erased. Equality checks bind output to the entire structured State and Questions, not object identity. CSV serializes objects as JSON text rather than `[object Object]`. Renaming a batch stores `displayName` and `nameUpdatedAt` outside its immutable input snapshot. Merges choose the latest rename independently of run progress, while deletion tombstones still win. Rename writes are validated and persisted before replacing in-memory data; a failed write cannot appear successful. Display names are used in the history, comparison, deletion confirmation, CSV and backups, while raw backups retain both original and display names. Each completed or failed attempt is recorded independently; Stop prevents remaining calls after the current request finishes. Reload does not replay unfinished calls: their batch is marked interrupted. Repetition can legitimately return identical values, including with the engine's internal cache; no client-side response duplication or synthetic noise is used.

Expected Choice compares the returned label. Expected Score compares the highest-probability ordinal level (ties do not match), not a rounded weighted mean. Expected Noul compares a Boolean using P(true) >= 0.5. Unset expectations and failed requests do not enter the agreement denominator. Per-question metrics show mean/range of scores, P(true), or probability of the expected/modal Choice label. Consistency is the modal complete answer combination's frequency, not correctness. Metrics are computed within each frozen batch, never pooled across languages or changed prompts. Individual runs remain inspectable using #1/#2/etc.

### Probability-based acceptance and the bundled preset

`evaluateAnswer` requires both the expected value and its optional minimum probability. It uses P(true) for expected true, 1−P(true) for expected false, and the distribution's probability of the expected Choice/Score key for the other types. It never thresholds the raw API `confidence` field, the weighted mean Score, or an aggregate result. Boundaries are inclusive with 1e−12 floating-point tolerance. Missing thresholds preserve legacy label-only semantics. `matches` remains label agreement; `passes` counts label plus threshold. A correct label with insufficient probability fails with `low-probability`; a wrong label fails even with a zero threshold. A run passes only if all of its configured expectations pass; zero expectations means unscored, not passed. API failures/deleted runs are excluded from evaluated denominators and displayed separately.

Summary, comparison and the history's Expected column use per-execution pass counts. Means cannot hide failing individual runs. Each original threshold and label is frozen with its batch; later explicit corrections are separate metadata and always stay out of model prompts. CSV uses current corrected expectations and preserves its previous columns including `min_probability`, `expected_probability`, `passes`, and `run_passes` (probabilities on a 0–1 scale). Existing saved tests are not relabeled or assigned thresholds automatically. The UI offers styled New test/CSV buttons on both pages, with no Backup or Import buttons; the legacy archive parser remains available for compatibility and regression fixtures.

The bundled prototype and six variants now reproduce the user's workbook-v2 Questions, full States, and expected labels, as authorized after the audit. Independent minimum-probability gates remain unchanged, not fitted to the observed spreadsheet outcomes. These are initial test specifications, not calibrated correctness probabilities or independently adjudicated ground truth. Use example restores all eleven automatically, without inference or training; existing saved snapshots and custom drafts remain unchanged. See TEST_AUDIT.md and the read-only workbook regression tests for differences and limitations.

### Deleting test data

Execution batches have an explicit Delete action with confirmation. Deleting a batch preserves any legacy case records. In an inspected batch, Delete #N removes just that attempt's response/error and recalculates statistics and CSV without it. The remaining run numbers are stable. The original requested count remains visible alongside the number deleted. Active batches cannot be deleted in their owning tab. The pure data module retains case-deletion compatibility, but it is no longer exposed in the interface.

Bulk Delete snapshots only the checked IDs, confirms the count and names, then applies existing tombstone deletions to a merged candidate archive in one storage write. A validation, active-batch or storage failure leaves the original in-memory and persisted archive intact; unselected tests and legacy cases are never included. Already-removed IDs are skipped. Checkboxes and bulk controls are disabled during a local execution batch, and any selected running batch prevents bulk deletion.

Deletions are committed to browser storage before being displayed as successful. If storage fails, the original data stays available. Minimal ID-only tombstones (up to 10,000 per collection), and ordinal-only deleted-run markers, prevent older tabs from restoring removed content when they save. No removed response is kept in a tombstone. Explicit backup import restores removed records under new IDs; imports never apply a backup's deletion list to the user's current library. Recovery requires a backup made before deletion. Clearing all browser storage remains outside this guarantee, and simultaneous tab writes are reconciled by storage events, not a transactional database.

### Weight retraining: currently blocked, not simulated

Expected answers are evaluation labels only. Saving or correcting them does **not** train any model, update weights, add a learned classifier layer, or inject examples into inference prompts. The official provider performs inference only; the optional local provider still uses unmodified, pinned jevos-v3 weights.

The official hosted Jev is a separate service. Its [Customizing Jev documentation](https://docs.typesafe.ai/models#customizing-jev), checked on 2026-10-03, explicitly says that customer-specific fine-tuning/LoRA is not offered and the same weights serve every account. An API key grants inference access, not model retraining. Domain customization uses State, instructions and criteria. The user subsequently authorized sending State and Questions to the official API and configured a private `.env` key. That integration is now active, with key handling and API usage as described above. No training workflow was added.

On 2026-10-03, inspection of the [official jevos-v3 release](https://github.com/feder-cr/jev/releases/tag/jevos-v3), public repository tree and Hugging Face model search found the OpenVINO INT8 and quantized GGUF distributions, but no original trainable jevos-v3 checkpoint/configuration or published fine-tuning pipeline. The upstream [OpenVINO exporter](https://github.com/feder-cr/jev/blob/main/export/export_openvino.py) expects an existing trained Hugging Face model directory and is not a training script. This is a finding about the inspected sources, not proof that the author cannot supply a checkpoint.

The inspected machine also had only about 2.2 GB of free space on the project filesystem and 2.6 GiB of available RAM (7.5 GiB total), with no NVIDIA tool detected. No large packages or alternate models were installed, and no external training service was used. Finishing actual jevos weight retraining requires the compatible checkpoint and an adequate training environment; switching models or using a remote service needs the user's direction.

Once those prerequisites are resolved, the training workflow must remain opt-in, preserve the original weights, use explicitly corrected labels, isolate training from held-out evaluation by source example, compare baseline/candidate on the same held-out inputs, record checkpoint and dataset hashes, and allow explicit activation and rollback. Weight changes and training-set improvement are not evidence of general improvement; no promise of monotonically better results per correction is valid.

## Retention and source traceability

Raw recognition records are keyed by run and result index. Interim text updates rather than appends, replayed final results do not duplicate, and interrupted hypotheses are marked unconfirmed. Records retain the original text, source offsets and approximate word-event marks. Window `sources` refer back to these records.

Session data, windows, question config and completed results are checkpointed in the same tab's `sessionStorage`. This is not permanent archival storage; use the download icon to save the full JSON. Storage errors leave in-memory capture running and display a warning. Older saved transcripts remain in the log but are not retrospectively given fabricated temporal boundaries.

`window.norteSession.getSnapshot()` exports schema version 2, meeting metadata, takes, records, segments, raw text, raw temporal packets, derived `classifierInputs` and classifier data. `getPackets()` returns raw windows with context `none`; `getClassifierInputs()` returns the exact model inputs with their overlap policy and source offsets. `window.NorteClassifier.snapshot()` includes actual requests/responses.

## Verification

```sh
node --test tests/transcription.test.cjs tests/windows.test.cjs tests/experiments.test.cjs
python3 -m unittest discover -s tests -p 'test_*.py'
node tests/browser-smoke.cjs
# Optional broad regression with an explicitly configured LOCAL server only:
NORTE_TEST_URL=http://127.0.0.1:8000 node tests/browser-smoke.cjs
# Exactly one paid example call, only with explicit authorization:
NORTE_ALLOW_PAID_TEST=1 node tests/browser-official.cjs
# Repeat UI checks using the captured result, without another paid call:
NORTE_OFFICIAL_REPLAY=/tmp/norte-official-verified.json node tests/browser-official.cjs
```

The browser test mocks voice events but sends resulting windows to the real local model when NORTE_TEST_URL is set. It checks real mouse dragging and splitter persistence, monospace 12px transcription, no Key points, both user-reported trailing-word regressions against the local model, five viewport widths, tabs, directional docking, internal/workspace keyboard resizing, actual typed answers and percentages, live State, JSON validation/application, meeting metadata, audio restarts, late finals and reload. Data tests cover 5-second minimums, 650 ms pauses, 15-second hard limits, short manual tails, revisions, exact raw-source retention and isolation at identical timestamps across takes.

Manual voice testing is still needed for real microphone pause sensitivity and recognition quality. The small synthetic Portuguese probe observed roughly 0.34–0.75 s warm inference for the three default questions, and a 1.68 s cold/new-shape request. These measurements exclude the 5–15 second capture window and upstream speech recognition latency; they are not guaranteed performance.
